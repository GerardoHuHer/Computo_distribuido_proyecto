# Rover Supervisor

A distributed system that emulates a space rover control center. It was built for the Distributed Computing course and is composed of several independent services that communicate over the Erlang distribution protocol.

- Backends: Elixir with the Phoenix framework (Central, Rover, Inventario).
- Middleware: Elixir with Phoenix, acting as API gateway and load balancer.
- Frontend: TypeScript with React and Vite, served by Nginx. It provides a terminal-style interface.
- Databases: one PostgreSQL 18 instance per backend.
- CI/CD: Jenkins running in a container.
- Infrastructure: Vagrant (libvirt) definitions for three Kali Linux virtual machines.

## Services

| Service | Directory | Description |
|---|---|---|
| Rover | `rover/` | CRUD for rovers. Generates a random event every minute and sends it to Central. |
| Inventario | `inventario/` | CRUD for inventory items. |
| Central | `central/` | Receives the events generated by the rovers and exposes CRUD operations over them. |
| Middleware | `middleware/` | Single entry point of the system. Validates requests, queues them and distributes them among the backend nodes. |
| Frontend | `central_front/` | Web terminal that sends commands to the middleware. |

Each backend owns its own PostgreSQL database (`db_central`, `db_vehiculo`, `db_inventario`). The middleware has no database.

## Architecture

The project starts from an MVC layout in which the controller layer (the backend) is split into three independent services: Rover, Inventario and Central. A middleware sits in front of them and the frontend only talks to the middleware.

```
Browser
   |
   v
Frontend (Nginx, port 80)
   |  /api/*
   v
Middleware (Phoenix, gateway + queues)
   |  Erlang distribution (GenStage)
   +--> Rover nodes       --> db_vehiculo
   +--> Inventario nodes  --> db_inventario
   +--> Central nodes     --> db_central
                ^
                |  recibir_evento (every minute)
         Rover nodes
```

### Communication between nodes

- All Elixir nodes join the same Erlang cluster. Node discovery is done with `libcluster` using the Gossip strategy, and the nodes share the cookie defined in `RELEASE_COOKIE`.
- The middleware owns one `GenStage` producer queue per backend type (`cola_rover`, `cola_inventario`, `cola_central`). Each queue holds up to 1000 pending requests; beyond that the middleware answers with `503`.
- Every backend node runs a `GenStage` consumer that subscribes to the producer queue of its type on the middleware node. The consumer demands events in batches (`max_demand: 10`, `min_demand: 5`) and processes them concurrently.
- Because consumers pull work according to their demand, requests are spread automatically among all available nodes of a given backend. Adding more instances of a backend increases throughput without any change to the middleware.
- If the subscription is lost, the consumer retries every second.

### Rover event flow

`Rover.GenerateEvento` is a `GenServer` that loads the event catalog into the database on start and then, every minute, picks a random event and sends it to the Central service through the middleware queue using the `recibir_evento` action.

## Requirements

- Docker with the Compose plugin
- Make
- 16 GB of RAM (recommended, the full stack runs several Elixir nodes and four PostgreSQL containers)

On Fedora, `install_dependencies.sh` installs Docker Engine, the Compose plugin, `make` and `gcc`.

## Quick Start

1. Create the environment file from the template:

   ```
   cp .env.example .env
   ```

2. Build the images, start the containers and run the database migrations:

   ```
   make setup
   ```

3. Open the frontend at `http://localhost`. The middleware is also reachable directly at `http://localhost:4002`.

To stop everything:

```
make down
```

## Configuration

All variables live in `.env` (see `.env.example` for defaults).

| Variable | Description |
|---|---|
| `RELEASE_COOKIE` | Erlang cookie shared by every node. Must be identical across services. |
| `POSTGRES_*`, `DB_HOST` | Credentials and host of the Central database. |
| `ROVER1_POSTGRES_*`, `ROVER1_DB_HOST` | Credentials and host of the Rover database. |
| `INVENTARIO1_POSTGRES_*`, `INVENTARIO1_DB_HOST` | Credentials and host of the Inventario database. |
| `MIDDLEWARE_*` | Middleware settings. `MIDDLEWARE_PORT` is the port published on the host (default `4002`). |

Default host ports:

| Port | Service |
|---|---|
| 80 | Frontend |
| 4002 | Middleware |
| 5432 | PostgreSQL (Central) |
| 5433 | PostgreSQL (Rover) |
| 5435 | PostgreSQL (Inventario) |
| 9090 | Jenkins UI |

Change the default credentials and cookie before deploying anywhere other than a local machine.

## API

The middleware exposes a single endpoint that routes every request to the right backend:

```
POST /api/gateway
Content-Type: application/json

{
  "type": "rover",
  "action": "create_rover",
  "params": { "pos_x": 10, "pos_y": 20 }
}
```

- `type` selects the backend: `rover`, `inventario` or `central`.
- `action` selects the operation.
- `params` is optional and defaults to an empty map.

Example:

```
curl -X POST http://localhost:4002/api/gateway \
  -H "Content-Type: application/json" \
  -d '{"type":"rover","action":"get_all_vehiculos"}'
```

### Available actions

| Type | Actions |
|---|---|
| `rover` | `create_rover`, `get_all_vehiculos`, `get_vehiculo`, `move_vehiculo`, `get_evento_random`, `delete_vehiculo` |
| `inventario` | `create_item`, `get_items`, `update_item`, `delete_item` |
| `central` | `recibir_evento`, `read_all_events`, `update_event`, `delete_event` |

### Error responses

| Status | Meaning |
|---|---|
| 400 | Missing or invalid `type` or `action`. |
| 404 | Resource not found. |
| 502 | The backend returned an unexpected error. |
| 503 | No backend available, or the queue is full. |

### Debug endpoint

```
GET /api/debug/nodos
```

Returns the nodes currently connected to the middleware, grouped by service type.

## Frontend Terminal

The frontend is a terminal emulator that translates commands into gateway requests. Arguments with spaces can be quoted.

```
list rover
get rover <id>
create rover <pos_x> <pos_y>
move rover <id> <pos_x> <pos_y>
delete rover <id>
event rover
load rover

list inventario
create inventario <name> <description> <cantidad> <prioridad>
update inventario <id> <name> <description> <cantidad> <prioridad>
delete inventario <id>

list central
create central <name> <description> <pos_x> <pos_y>
update central <id> <name> <description> <pos_x> <pos_y>
delete central <id>
```

Nginx serves the static build and proxies `/api/` to the middleware container.

## Scaling and Load Balancing

Start several instances of every Elixir backend:

```
make scale INS=3
```

Verify that the new nodes joined the cluster:

```
curl http://localhost:4002/api/debug/nodos
```

Two helper scripts are provided at the repository root:

| Script | Description |
|---|---|
| `./test_routes.sh` | Functional test that calls every action of every backend through the gateway. Set `MIDDLEWARE_URL` to override the default `http://localhost:4002`. |
| `./test_load_balancer.sh [total] [concurrency]` | Sends concurrent `create_rover` requests (defaults: 50 requests, concurrency 10) to check that work is distributed among instances. |

## Testing

Run the ExUnit suites of the Elixir services inside containers:

```
make test
```

Test services are defined under the `test` Compose profile and run against their own database containers.

## Infrastructure

The `infrastructure/` directory contains a `Vagrantfile` that provisions three Kali Linux virtual machines (`kali-rover`, `kali-inventario`, `kali-central`) with the libvirt provider.

- Box: `kalilinux/rolling`, version `2026.2.0`.
- Resources per VM: 2 CPUs and 3072 MB of RAM.
- Network: isolated private network `lab_interna` (`10.10.10.0/24`), with addresses `10.10.10.10`, `10.10.10.11` and `10.10.10.12`.
- Provisioning: `scripts/setup.sh` installs Docker, enables it and adds the `vagrant` user to the `docker` group.

```
cd infrastructure
vagrant up
```

A Terraform proposal for hosting the project is planned.
